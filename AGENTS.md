## App WebView ↔ remote pages (system bars, safe areas)

- The app runs the admin portal **remote** (`clood-x.com/index.php#app_sso=1`) inside the same WebView. `window.Capacitor` is NOT injected on remote pages (JSInjector is pinned to the app origin), BUT `window.androidBridge` IS — `WebViewCompat.addWebMessageListener` is registered for all `allowNavigation` origins (MessageHandler.java). Remote pages can call plugins by posting raw bridge JSON: `androidBridge.postMessage(JSON.stringify({callbackId, pluginId, methodName, options}))`; replies arrive on `androidBridge.onmessage` (`{callbackId, data}`).
- `DocumentViewer` plugin (custom, registered in MainActivity) exposes `setSystemBarStyle({darkIcons})` (status+nav bar icon colour) and `getSafeAreaInsets()` → `{top,bottom}` in CSS px. `index.php` calls both: bars follow `data-theme` via a MutationObserver, insets land in `--safe-top`/`--safe-bottom` CSS vars.
- **iOS injector opt-out**: SceneDelegate `injectSafeAreaScript()` (atDocumentEnd) pads `body` by the insets AND runs a `patch()` heuristic on every DOM mutation that permanently inline-pads any fixed/sticky element found at the viewport edge. Bug: the admin `.topbar` is `sticky` — whenever a SPA navigation happens while scrolled, it is at top:0 → gets +59px padding on top of the body padding → ~120px gap that "comes back" after navigating. The injector bails on `window.__cxSafeArea` — index.php sets it to 1 whenever `app-shell` is active, so the page owns its insets (like the bundled localhost pages do). Do NOT remove that flag.
- Edge-to-edge CSS contract (`html.app-shell` in index.php `<style>`): `--sa-top: var(--safe-top, env(safe-area-inset-top,0px))` (same for bottom). Android → `--safe-top` pushed natively (env() is 0 there); iOS → env() (viewport-fit=cover). Fixed/sticky chrome (topbar, sidebar, FABs, chat panel, toasts) pads by `--sa-*`; backgrounds still extend under the bars. style.css `@media ≤640px .topbar` uses `--sa-top` too.
- `login.php` also runs in the app WebView (SSO expiry fallback) — hardcodes `darkIcons:false` (light icons on the dark gradient) and `viewport-fit=cover`.

## Bereich scope (per-user area restriction)

- `central_users.allowed_bereiche` (JSON whitelist, lowercased compare) scopes a tenant user to named Bereiche. NULL/empty = unrestricted; `is_owner`/`tenant_admin`/`super_admin` always bypass.
- ALL enforcement lives in `app/Support/BereichScope.php` — never hand-roll bereich checks. List queries: `*Predicate()`/`inList(derivedExprSub|derivedExpr)`; single records: `allows*()` (404 on out-of-scope); creates: `bereichInputAllowed`/`bereicheInputAllowed`; UPDATES: `bereichWriteAllowed`/`bereicheWriteAllowed` (unchanged stored tags always pass — a restricted user may edit a multi-service entity he sees via a secondary tag, and `outOfScopeValues()` re-merges tags he cannot see so his save never strips them).
- Effective Bereich of operational rows (einsaetze/bestellungen/bestelleingang): `artikel.bereich` → fallback `kunden.bereich`. Customers/objects/workers/NU carry `bereich` (primary) + `bereiche` JSON (multi-service list — entity visible when ANY tag matches); matching is comma-aware everywhere via `tagMatchSql`/`matchBereichExpr`. Workers/NU use pool semantics (untagged = shared, visible to all restricted users).
- Managed catalog `bereiche_katalog` (tenant): mains (`parent_id` NULL) feed every `bereiche` picker, subs feed `objekte.art`/`arten` (Objektart multi-list). `BereichCatalogController` — read: all users (scope-filtered), write: admins + `stammdaten.*.edit`, restricted managers may only touch rows inside their own whitelist. Renames propagate to all tagged columns + `central_users.allowed_bereiche`. Frontend tab: Konto & Firma → Bereiche. Guards: `artenWriteAllowed`/`outOfScopeArten`; subs picker via `subOptionsFor`.
- Rule for NEW endpoints touching tenant data: apply BereichScope or the restricted user leaks. Aggregation SQL must include the predicate BEFORE grouping. Cache keys must include the user's scope.
- Verify on server after changes: `php -l`, `install -o www-data -g www-data -m 644`, `systemctl restart hms-octane`. Rollback backups land in `/tmp/bereich_backup_*`.

## Bestelleingang ↔ Dispo consistency rules (since 2026-10-10)

- The Bestelleingang order is the source of every linked einsatz. `IncomingOrderController::matchDaysToEinsaetze()` pairs day rows with shifts of the same date: pass 1 = same start/end time, pass 2 = rest (booked shifts preferred on exact time, avoided on mismatch). syncDownstream AND the update() removal check both use it — never re-implement the pairing.
- "Booked" = confirmed, or `pruefung='geplant'` with internal workers OR NU workers (`nu_position_zuweisungen`). One definition: `App\Support\StaffedShifts` (+ `IncomingOrderController::isStaffedShift`). Booked shifts keep times/crew on order edits (ort + pause still sync for planned), and block: removing their day, removing their Leistung, deleting the order (confirmed ones are unlinked as history instead), deleting the Bestellung, permanently deleting the Objekt. Responses are 409 with `blocked_shifts` (frontend shows an mdAlert list).
- Dispo `DELETE /tasks/{id}` is refused (409 + `eingang_id`) for live shifts of an existing order — remove the day in Bestelleingang. Grey tombstones (`bestell_storno_at`) and manual shifts without order stay deletable. `DELETE /orders/{id}` is refused while the Bestelleingang order exists.
- `einsaetze.tag_nr` links a shift to its order row (Dispo reads plan time/Menge/Beschreibung via datum+tag_nr). syncDownstream keeps it current for protected shifts too.
- Removing an unbooked shift via order edit also deletes its NU positions, closes open clock-ins and queues NU cancellation mails after commit.
- Days outside the order month are allowed (multi-month orders exist); the wizard warns only for newly added dates (`wizConfirmOutOfMonth`). Duplicate check = same date + Leistung + start/end time (`wizConfirmDuplicateDays`).
- Regression suite: `tmp_verify/be_dispo_full.php` (34 checks, staging DDR tenant, one transaction rolled back, mail/queue faked). Run as www-data in `/var/www/hms-backend-staging`: `php artisan tinker /tmp/be_dispo_full.php`. DDR exists only in `hms_central_staging`.

## Dispo ↔ Nachunternehmer (NU) rules (since 2026-10-10)

- `einsaetze.nu_id` mirrors the NU positions (`App\Support\NuLink::resolve/sync`): saveAssignment never takes it from the client (hidden field can be stale), saveNuPositions/rejectShift re-point it when another NU still has positions. Controlling's NU branch + NU cost hang on it.
- NU portal: every position/worker endpoint checks ownership against the token's nu_id (positions(), updateWorker() were open before). updateWorker is a partial update. assignWorker rejects inactive workers, grey (bestell_storno_at) shifts and overlapping shifts of the same worker (`NuLink::overlaps`). deleteWorker is refused while the worker has zuweisungen (his confirmed hours would vanish from the Abrechnung — deactivate instead). Grey shifts are hidden in shifts() and cannot be accepted.
- saveNuPositions: refused on grey shifts; Anzahl may not drop below assigned NU workers; removing staffed positions mails the NU (nu-worker-removal); full cancellation of a planned shift without any staff un-plans it.
- Times change only via Bestelleingang: syncDownstream mails `emails.nu-time-change` to NUs with positions on a re-timed (unbooked) shift, after commit.

## Cloudflare asset cache — never reuse a `?v=` string

- Static assets go through Cloudflare with `cache-control: public, max-age=604800` (7 days), keyed by the full URL incl. `?v=`. Once a `?v=` value has ever been requested, Cloudflare keeps serving THAT file for a week, even after the file on disk changes.
- Re-using a version string from an earlier session (e.g. `20261018ph3` on staging) silently serves stale code. Always pick a fresh, never-used value when bumping.
- Verify after deploy by checking content, not just HTTP 200: `curl -sk -D- "https://<host>/assets/js/x.js?v=NEW" | grep -i cf-cache-status` plus a grep for a new identifier in the body.

## UI rules — Material Design 3 is the ONLY component system (binding for all new/changed UI)

Goal of the MD3 migration: one look everywhere, and new screens are ASSEMBLED from existing components — never re-implemented. Details/history: `docs/MD3_ADOPTION.md`.

- **Use the shipped `@material/web` element** (vendored `assets/js/material-web.bundle.js`) for every interactive control: buttons `md-filled|outlined|text|filled-tonal-button`, icon buttons `md-icon-button`, fields `md-outlined-text-field` (incl. `type="textarea"`), `md-outlined-select`+`md-select-option`, `md-checkbox`, `md-radio`, `md-switch`, chips `md-assist|filter|input-chip` in `md-chip-set`, `md-tabs`+`md-primary-tab`, `md-menu`, `md-list`, `md-dialog`, `md-circular|linear-progress`, `md-divider`.
- **For what the bundle does not ship, use the shared layer** — `assets/js/ui-components.js` + `assets/css/ui-components.css` (loaded in index.php): `uiCard()`, `uiToolbar()`, `uiEmptyState()`, `uiBadge()`, `uiActions()`, plus convenience wrappers `uiButton()`, `uiIconButton()`, `uiChip()/uiChips()`, `uiTabs()/uiBindTabs()`, `uiIcon()`. Prefer the helpers over hand-written md markup — they keep variants, icon slots, escaping and accessible names consistent.
- **Forbidden in new code**: native `<button>`/`<input>`/`<select>`/`<textarea>` for visible controls (exceptions below); new `.btn*`/`*-btn`/`*-chip`/`*-pill`/`*-tab`/`*-card`/`*-overlay`/`*-empty` classes that restyle a control or container from scratch; Font Awesome (`fa-*`); hex/rgb colours, raw `border-radius` px, raw `box-shadow`; new `<style>` blocks injected from JS. A missing variant goes into `ui-components.css` as a modifier (`.ui-badge.is-*`, `md-btn-*`, `md-icon-*`) — never into a module stylesheet.
- **Tokens only**: colours `--md-sys-color-*` / `--md-ext-color-{success,warning,info}*`; shape `--md-sys-shape-corner-*`; elevation `--md-sys-elevation-level*`; type `--md-sys-typescale-*`; motion `--md-sys-motion-*`. Bereich colours ONLY via the `bereichColor*` helpers in app.js. Icons: Material Symbols ligatures (`uiIcon()`), check the name exists — unknown names render as literal text.
- **Module CSS is for layout only** (grid/flex/spacing of the page). If a rule sets background + border + radius + padding on a control, it is re-implementing a component — use the md element instead.
- **Dialogs**: `openModal()` (shared `md-dialog#modalOverlay`) or a page-owned `<md-dialog>`; no new overlay systems.
- **JS↔md compatibility** (verified in bundle source): `[checked]` not `:checked` for md-checkbox/radio, md-switch uses `.selected`; `focusin`/`focusout` not `focus`/`blur`; `querySelector('input')` misses md fields; `document.activeElement` is the md HOST — tag guards must include `MD-*`; `input`/`change`/key events are composed.
- **Allowed exceptions** (documented, don't convert): `<input type="file">` (no md component, hide it behind a md button), hidden inputs, native controls inside pages WITHOUT the bundle (see below), the Dispo planner board, PDF designer, calendars, data tables, Tailwind marketing pages.
- **Pages without the bundle**: only `index.php` and `nu_portal.php` load material-web. `md-*` emitted anywhere else renders as an unknown inline element. Standalone pages are covered by `assets/css/auth-md3.css` (native controls styled with the same MD3 tokens) — new standalone pages link it instead of writing their own form CSS.
- **Before committing UI**: render it (headless Chrome repro or staging) — custom elements break silently; bump `?v=` of every touched asset (index.php links AND `PAGE_MODULE_SCRIPTS`/`TASKS_MODULE_SCRIPTS` in app.js); check new CSS parses (an unclosed `var(` once swallowed 290 rules of users.css).
